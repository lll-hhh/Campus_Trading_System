# 第7章 权限管理与安全

## 7.1 RBAC权限模型

### 7.1.1 权限体系设计

本系统采用基于角色的访问控制（Role-Based Access Control, RBAC）模型，这是目前企业级应用中最广泛使用的权限管理方案。RBAC通过将权限授予角色，再将角色分配给用户的方式，实现了权限管理的灵活性和可维护性。相比直接为用户分配权限（ACL模型），RBAC的优势在于：第一，简化权限管理，当需要调整某类用户的权限时，只需修改角色权限，所有拥有该角色的用户权限自动更新；第二，职责分离，用户的权限由其职责（角色）决定，符合最小权限原则；第三，易于审计，可以清晰地追踪每个用户通过哪些角色获得了哪些权限；第四，支持权限继承和组合，一个用户可以拥有多个角色，最终权限是所有角色权限的并集。

**RBAC核心概念解析：**

**用户（User）**：系统的操作主体，每个用户拥有唯一的身份标识（用户ID）。用户通过用户名密码或第三方OAuth登录系统，获得JWT Token作为身份凭证。用户表存储基本信息（用户名、邮箱、手机号）、认证信息（密码哈希）、状态信息（激活状态、封禁状态）和元数据（注册时间、最后登录时间）。

**角色（Role）**：权限的集合，代表系统中的一种职责或岗位。角色具有名称（role_name）、描述（description）、状态（status）等属性。系统预定义了五种核心角色：admin（系统管理员）、moderator（内容审核员）、seller（供应商）、user（普通用户）、vip（VIP用户）。角色可以动态创建和删除，管理员可以通过后台管理界面创建自定义角色，如"客服"、"财务"等。

**权限（Permission）**：对系统资源执行操作的授权，是权限控制的最小单元。权限采用"资源:操作"的命名规范，清晰表达权限的含义。例如`items:create`表示创建零件的权限，`users:ban`表示封禁用户的权限。权限表包含permission_code（权限代码，唯一标识）、permission_name（权限名称，用于展示）、resource（资源类型）、action（操作类型）等字段。

**用户-角色关联（UserRole）**：多对多关系表，记录用户拥有哪些角色。一个用户可以拥有多个角色，一个角色可以分配给多个用户。关联表包含user_id、role_id、assigned_at（分配时间）、assigned_by（分配操作人）等字段，支持审计追踪。

**角色-权限关联（RolePermission）**：多对多关系表，记录角色拥有哪些权限。一个角色可以拥有多个权限，一个权限可以授予多个角色。关联表包含role_id、permission_id、granted_at（授权时间）等字段。

**权限层级结构设计：**

系统的权限按照资源类型划分为五大模块，每个模块包含若干具体权限，形成树状层级结构。这种结构便于理解和管理，管理员可以按照模块批量授权。

```
系统权限体系（共50+权限）
├── 用户管理模块（User Management）
│   ├── users:view（查看用户列表和详情）
│   │   - 权限说明：查看所有用户的基本信息（用户名、注册时间、状态等）
│   │   - 适用角色：admin、moderator

│   │   - 权限说明：通过后台手动创建用户账号，设置初始密码
│   │   - 适用角色：admin
│   │   - 使用场景：批量导入用户、为员工创建账号
│   ├── users:edit（编辑用户信息）
│   │   - 权限说明：修改用户的基本信息、角色分配、状态设置
│   │   - 适用角色：admin
│   │   - 使用场景：用户信息维护、角色调整、邮箱更正
│   ├── users:delete（删除用户）
│   │   - 权限说明：永久删除用户账号及其所有关联数据
│   │   - 适用角色：admin（超级管理员）
│   │   - 使用场景：清理测试账号、删除违规用户
│   │   - 注意事项：删除前需确认用户无未完成交易，使用软删除更安全
│   ├── users:ban（封禁/解封用户）
│   │   - 权限说明：将用户状态设置为banned，禁止登录和操作
│   │   - 适用角色：admin、moderator
│   │   - 使用场景：处理违规用户、响应举报、临时冻结账户
│   │   - 实现机制：修改user.status字段，JWT验证时检查状态

│       - 权限说明：为用户重置密码（用户忘记密码时）
│       - 适用角色：admin
│       - 使用场景：用户申诉、密码找回
│
├── 零件管理模块（Item Management）
│   ├── items:view（查看零件）
│   │   - 权限说明：查看所有零件信息，包括未上架和已删除的零件
│   │   - 适用角色：所有角色（user、seller、admin等）
│   │   - 使用场景：零件浏览、搜索、详情查看
│   ├── items:create（发布零件）
│   │   - 权限说明：创建新的零件条目，上传图片，设置价格和描述
│   │   - 适用角色：seller、admin
│   │   - 使用场景：供应商发布汽配零件
│   │   - 业务规则：用户需通过实名认证才能获得seller角色
│   ├── items:edit（编辑自己的零件）
│   │   - 权限说明：修改自己发布的零件信息（标题、描述、价格、图片）
│   │   - 适用角色：seller（仅限编辑自己的零件）
│   │   - 使用场景：零件信息更新、价格调整、图片更换
│   │   - 权限检查：除权限验证外，还需验证item.seller_id == current_user.id
│   ├── items:edit_any（编辑任意零件）
│   │   - 权限说明：修改任何用户发布的零件（管理员特权）
│   │   - 适用角色：admin
│   │   - 使用场景：纠正零件错误信息、移除违规内容
│   ├── items:delete（删除自己的零件）
│   │   - 权限说明：删除自己发布的零件（软删除，标记为deleted）
│   │   - 适用角色：seller
│   │   - 使用场景：零件已售出、不再出售
│   │   - 实现方式：软删除（is_deleted=true），保留数据用于统计和审计
│   ├── items:delete_any（删除任意零件）
│   │   - 权限说明：删除任何违规或不当的零件
│   │   - 适用角色：admin、moderator
│   │   - 使用场景：处理违规零件、响应举报
│   ├── items:audit（审核零件）
│   │   - 权限说明：审核待上架零件，决定是否允许公开展示
│   │   - 适用角色：moderator、admin
│   │   - 使用场景：新发布零件审核、举报零件复审
│   │   - 审核流程：检查标题描述是否合规、图片是否合规、价格是否合理
│   └── items:feature（设置零件为推荐）
│       - 权限说明：将零件设为首页推荐或热门推荐
│       - 适用角色：admin
│       - 使用场景：运营推广、活动零件
│
├── 交易管理模块（Transaction Management）
│   ├── transactions:view（查看交易）
│   │   - 权限说明：查看自己参与的交易（采购商或供应商）
│   │   - 适用角色：user（所有用户）
│   │   - 使用场景：查看订单列表、交易详情、物流信息
│   │   - 权限检查：tx.buyer_id == user.id OR tx.seller_id == user.id
│   ├── transactions:view_any（查看所有交易）
│   │   - 权限说明：查看系统中的所有交易记录
│   │   - 适用角色：admin
│   │   - 使用场景：交易监控、数据分析、纠纷处理
│   ├── transactions:manage（管理交易）
│   │   - 权限说明：修改交易状态、强制取消订单、介入纠纷
│   │   - 适用角色：admin
│   │   - 使用场景：处理交易纠纷、异常订单处理、退款申请
│   ├── transactions:refund（退款处理）
│   │   - 权限说明：审批退款申请，执行退款操作
│   │   - 适用角色：admin
│   │   - 使用场景：采购商申请退款、交易纠纷退款
│   │   - 业务规则：退款需验证交易状态、支付状态、退款原因
│   └── transactions:cancel（取消交易）
│       - 权限说明：取消进行中的交易
│       - 适用角色：buyer、seller（自己的交易）、admin（任意交易）
│       - 使用场景：采购商反悔、供应商缺货、协商一致取消
│
├── 系统管理模块（System Management）
│   ├── system:config（系统配置）
│   │   - 权限说明：修改系统配置参数（如注册开关、上传大小限制）
│   │   - 适用角色：admin
│   │   - 使用场景：系统参数调优、功能开关控制
│   │   - 配置项：JWT过期时间、文件上传限制、邮件服务器、支付接口等
│   ├── system:logs（查看日志）
│   │   - 权限说明：查看系统运行日志、操作审计日志、错误日志
│   │   - 适用角色：admin
│   │   - 使用场景：问题排查、安全审计、性能分析
│   │   - 日志类型：访问日志、错误日志、慢查询日志、安全日志
│   ├── system:sync（同步管理）
│   │   - 权限说明：管理多数据库同步任务，查看同步状态，处理冲突
│   │   - 适用角色：admin
│   │   - 使用场景：启动/停止同步、查看同步延迟、解决冲突
│   ├── system:backup（数据备份）
│   │   - 权限说明：执行数据库备份和恢复操作
│   │   - 适用角色：admin
│   │   - 使用场景：定期备份、迁移前备份、灾难恢复
│   └── system:monitor（系统监控）
│       - 权限说明：查看系统性能指标、资源使用情况、告警信息
│       - 适用角色：admin
│       - 使用场景：性能监控、容量规划、故障预警
│
└── 内容管理模块（Content Management）
    ├── content:moderate（内容审核）
    │   - 权限说明：审核用户生成的内容（零件、评论、私信）
    │   - 适用角色：moderator、admin
    │   - 使用场景：敏感内容过滤、违规内容处理
    │   - 审核内容：零件标题描述、用户评论、私信举报
    ├── content:report（举报处理）
    │   - 权限说明：查看和处理用户举报
    │   - 适用角色：moderator、admin
    │   - 使用场景：用户投诉、违规举报、纠纷调解
    │   - 处理流程：查看举报详情→调查核实→采取措施→反馈用户
    ├── comments:delete（删除评论）
    │   - 权限说明：删除不当评论
    │   - 适用角色：moderator、admin
    │   - 使用场景：删除辱骂、广告、虚假评论
    └── messages:monitor（私信监控）
        - 权限说明：监控私信内容，检测违规行为
        - 适用角色：admin
        - 使用场景：反欺诈、反骚扰、敏感词监控
        - 隐私保护：仅在用户举报或系统告警时查看，记录查看日志
```

**角色定义和权限分配：**

系统预定义了五种核心角色，每种角色拥有不同的权限组合，满足不同用户群体的需求。角色设计遵循最小权限原则，用户只能获得完成其职责所必需的最小权限集。

**1. admin（系统管理员）- 全部权限**
- 权限数量：50+（所有权限）
- 职责描述：系统的最高权限管理者，负责系统配置、用户管理、数据管理等所有管理工作
- 权限范围：拥有所有模块的所有权限，可以执行任何操作
- 典型用户：系统开发人员、运维人员、超级管理员
- 安全机制：admin账号需要双因素认证（2FA），登录时发送验证码到手机

**2. moderator（内容审核员）- 审核权限**
- 权限列表：
  * users:view（查看用户）
  * users:ban（封禁用户）
  * items:view（查看零件）
  * items:audit（审核零件）
  * items:delete_any（删除零件）
  * content:moderate（内容审核）
  * content:report（举报处理）
  * comments:delete（删除评论）
  * transactions:view_any（查看交易）
- 职责描述：负责平台内容审核，处理用户举报，维护社区秩序
- 权限范围：主要集中在内容审核和用户管理，无系统配置和数据管理权限
- 典型用户：客服人员、社区管理员
- 工作流程：每日处理举报队列→审核待上架零件→处理违规内容→生成审核报告

**3. seller（供应商）- 零件发布权限**
- 权限列表：
  * items:view（查看零件）
  * items:create（发布零件）
  * items:edit（编辑自己的零件）
  * items:delete（删除自己的零件）
  * transactions:view（查看自己的交易）
  * transactions:cancel（取消自己的交易）
- 职责描述：在平台上发布和管理汽配零件，与采购商交易
- 权限范围：可以发布和管理自己的零件，查看自己的交易
- 获取条件：用户需通过实名认证（上传身份证照片），审核通过后自动获得seller角色
- 限制条件：信用分低于60分或被投诉超过3次，自动降级为user角色

**4. user（普通用户）- 基础权限**
- 权限列表：
  * items:view（查看零件）
  * transactions:view（查看自己的交易）
  * transactions:cancel（取消自己的交易）
  * comments:create（发表评论）
  * messages:send（发送私信）
  * favorites:manage（收藏管理）
- 职责描述：平台的基础用户，可以浏览零件、购买零件、发表评论
- 权限范围：只能进行基本的购买和社交操作，不能发布零件
- 典型用户：新注册用户、采购商用户
- 升级途径：申请实名认证→获得seller角色

**5. vip（VIP用户）- 增强权限**
- 权限列表：继承user的所有权限，额外增加：
  * items:feature_request（申请零件推荐位）
  * transactions:priority（优先交易）
  * support:vip（VIP客服通道）
- 职责描述：付费用户，享受增强功能和优先服务
- 权限范围：在普通用户基础上增加营销和服务权限
- 获取条件：充值成为VIP会员（月费/年费）
- 特权功能：零件优先展示、专属客服、交易手续费优惠

### 7.1.2 权限检查实现

权限检查是RBAC模型的核心执行机制，确保用户只能访问其被授权的资源和操作。本系统在多个层面实现了权限检查：后端API层（FastAPI依赖注入）、服务层（业务逻辑）、数据层（ORM查询过滤）。多层权限检查形成纵深防御，即使某一层被绕过，其他层仍能拦截非法访问，显著提升系统安全性。


**权限检查架构设计：**

权限检查采用装饰器模式和依赖注入模式相结合的方式实现，代码简洁且易于维护。核心设计思想是：将权限检查逻辑与业务逻辑分离，通过装饰器或依赖注入的方式自动执行权限检查，业务代码只需声明所需权限，无需编写重复的检查代码。这种设计符合AOP（面向切面编程）思想，将横切关注点（权限检查）与核心业务逻辑解耦。

**权限检查流程（7个步骤）：**

1. **提取用户身份**：从HTTP请求的Authorization Header中提取JWT Token，解码获取用户ID
2. **验证用户状态**：检查用户是否激活（status='active'），是否被封禁（status!='banned'）
3. **查询用户角色**：通过user_roles表查询用户拥有的所有角色
4. **查询角色权限**：通过role_permissions表查询所有角色拥有的所有权限（去重）
5. **权限匹配判断**：判断用户权限列表是否包含目标权限代码
6. **超级管理员豁免**：is_superuser=true的用户自动通过所有权限检查
7. **返回检查结果**：通过则继续执行业务逻辑，不通过则抛出403 Forbidden异常

**后端权限检查实现（FastAPI依赖注入）：**

```python
# core/security.py - 权限检查核心模块
from functools import wraps
from fastapi import HTTPException, status, Depends
from typing import List, Set
from sqlalchemy import select
from sqlalchemy.orm import Session
import logging

logger = logging.getLogger(__name__)

# ============================================
# 权限检查装饰器（装饰器模式）
# ============================================
def require_permissions(*required_permissions: str):
    """
    权限检查装饰器
    
    检查当前用户是否拥有指定的所有权限
    支持多权限检查（AND逻辑）：用户必须同时拥有所有指定权限
    
    使用场景:
    - 需要多个权限的操作（如删除零件需要items:delete + items:view）
    - 装饰器风格的权限控制（Python函数装饰器）
    
    参数:
        *required_permissions: 可变参数,需要的权限代码列表
    
    返回:
        装饰器函数
    
    示例:
        @router.delete("/items/{item_id}")
        @require_permissions("items:delete", "items:view")
        async def delete_item(item_id: int, current_user: User = Depends(get_current_user)):
            # 用户必须同时拥有items:delete和items:view权限才能执行到这里
            ...
    
    实现原理:
    1. 装饰器通过wraps保留原函数的元数据（函数名、文档等）
    2. wrapper函数拦截原函数调用,先执行权限检查
    3. 从kwargs中提取current_user（由FastAPI依赖注入）
    4. 查询用户权限并判断是否包含required_permissions
    5. 通过则调用原函数,不通过则抛出403异常
    """
    
    def decorator(func):
        @wraps(func)
        async def wrapper(*args, **kwargs):
            # 提取当前用户（由get_current_user依赖注入到kwargs）
            current_user = kwargs.get('current_user')
            
            # 身份验证检查
            if not current_user:
                logger.warning(f"Permission check failed: No current_user in kwargs")
                raise HTTPException(
                    status_code=status.HTTP_401_UNAUTHORIZED,
                    detail="Authentication required - Please login first"
                )
            
            # 超级管理员跳过权限检查（拥有所有权限）
            if current_user.is_superuser:
                logger.info(f"Superuser {current_user.username} bypassed permission check")
                return await func(*args, **kwargs)
            
            # 查询用户的所有权限
            user_permissions = get_user_permissions(current_user.id)
            
            # 记录权限检查日志（用于审计）
            logger.info(
                f"Permission check for user {current_user.username} (id={current_user.id}): "
                f"required={required_permissions}, has={len(user_permissions)} permissions"
            )
            
            # 检查是否拥有所需的所有权限（AND逻辑）
            missing_permissions = [
                perm for perm in required_permissions 
                if perm not in user_permissions
            ]
            
            if missing_permissions:
                logger.warning(
                    f"Permission denied for user {current_user.username}: "
                    f"missing permissions {missing_permissions}"
                )
                raise HTTPException(
                    status_code=status.HTTP_403_FORBIDDEN,
                    detail=f"Permission denied - Missing permissions: {', '.join(missing_permissions)}"
                )
            
            # 权限检查通过,执行原函数
            logger.info(f"Permission check passed for user {current_user.username}")
            return await func(*args, **kwargs)
        
        return wrapper
    return decorator

# ============================================
# 权限查询函数（数据库查询）
# ============================================
def get_user_permissions(user_id: int) -> Set[str]:
    """
    获取用户的所有权限（通过角色关联）
    
    查询逻辑:
    1. 通过user_roles表找到用户的所有角色
    2. 通过role_permissions表找到角色的所有权限
    3. 去重合并（一个用户可能通过多个角色获得同一权限）
    
    SQL等价:
    SELECT DISTINCT p.permission_code
    FROM permissions p
    JOIN role_permissions rp ON p.id = rp.permission_id
    JOIN user_roles ur ON rp.role_id = ur.role_id
    WHERE ur.user_id = ?
    
    参数:
        user_id: 用户ID
    
    返回:
        Set[str]: 权限代码集合（使用Set自动去重）
    
    性能优化:
    - 使用DISTINCT去重,减少Python处理
    - 只查询permission_code字段,减少数据传输
    - 可以添加Redis缓存,TTL=5分钟
    """
    
    with db_manager.session_scope("mysql") as session:
        # SQLAlchemy查询构建
        permissions = session.execute(
            select(Permission.permission_code)
            .distinct()  # 去重
            .join(RolePermission, RolePermission.permission_id == Permission.id)
            .join(UserRole, UserRole.role_id == RolePermission.role_id)
            .where(UserRole.user_id == user_id)
        ).scalars().all()
        
    # 转换为Set（支持快速查找,O(1)时间复杂度）
    permission_set = set(permissions)
    
    logger.debug(f"User {user_id} has {len(permission_set)} permissions: {permission_set}")
    
    return permission_set

# ============================================
# 权限缓存（性能优化）
# ============================================
from functools import lru_cache
from datetime import datetime, timedelta

# 用户权限缓存（LRU Cache,最多缓存1000个用户）
_permission_cache = {}
_cache_ttl = timedelta(minutes=5)  # 缓存5分钟

def get_user_permissions_cached(user_id: int) -> Set[str]:
    """
    获取用户权限（带缓存）
    
    缓存策略:
    - 使用内存LRU缓存,最多缓存1000个用户的权限
    - TTL=5分钟,5分钟后自动失效重新查询
    - 权限变更后需手动清除缓存
    
    适用场景:
    - 高频权限检查（每个API请求都检查）
    - 用户权限变更不频繁（大部分时间权限稳定）
    
    性能提升:
    - 缓存命中时,权限查询从10ms降低到<0.1ms
    - 减少数据库压力,提升并发能力
    """
    
    # 检查缓存是否存在且未过期
    if user_id in _permission_cache:
        cached_data, cached_time = _permission_cache[user_id]
        if datetime.now() - cached_time < _cache_ttl:
            logger.debug(f"Permission cache hit for user {user_id}")
            return cached_data
    
    # 缓存未命中或已过期,查询数据库
    logger.debug(f"Permission cache miss for user {user_id}, querying database")
    permissions = get_user_permissions(user_id)
    
    # 更新缓存
    _permission_cache[user_id] = (permissions, datetime.now())
    
    # 限制缓存大小（最多1000个用户）
    if len(_permission_cache) > 1000:
        # 删除最旧的缓存项
        oldest_user_id = min(_permission_cache.keys(), key=lambda k: _permission_cache[k][1])
        del _permission_cache[oldest_user_id]
        logger.debug(f"Permission cache evicted oldest entry: user {oldest_user_id}")
    
    return permissions

def clear_permission_cache(user_id: int = None):
    """
    清除权限缓存
    
    调用场景:
    - 用户角色变更后
    - 角色权限变更后
    - 管理员手动刷新缓存
    
    参数:
        user_id: 指定用户ID清除,None表示清除所有
    """
    if user_id is None:
        _permission_cache.clear()
        logger.info("Cleared all permission cache")
    elif user_id in _permission_cache:
        del _permission_cache[user_id]
        logger.info(f"Cleared permission cache for user {user_id}")
```

#### 资源所有权检查

除了基于角色的权限检查（RBAC），系统还实现了基于资源所有权的访问控制（ABAC - Attribute-Based Access Control的一种形式）。所有权检查确保用户只能访问和操作自己拥有的资源，即使用户拥有相应的权限，也不能操作他人的资源。这种双重验证机制（权限检查 + 所有权检查）提供了更细粒度的访问控制，符合最小权限原则和职责分离原则。

**所有权检查应用场景：**

1. **零件管理**：用户只能编辑/删除自己发布的零件，不能操作他人零件
2. **交易管理**：用户只能查看自己参与的交易（作为采购商或供应商），不能查看无关交易
3. **评论管理**：用户只能编辑/删除自己发表的评论
4. **消息管理**：用户只能查看发送给自己的消息或自己发送的消息
5. **收藏管理**：用户只能管理自己的收藏夹

**所有权检查实现（工厂函数 + 依赖注入）：**

```python
# core/security.py - 资源所有权检查模块

from enum import Enum
from typing import Union, Dict, Callable

# ============================================
# 资源类型枚举（支持的资源类型）
# ============================================
class ResourceType(str, Enum):
    """系统中需要所有权检查的资源类型"""
    ITEM = "item"              # 零件
    TRANSACTION = "transaction"  # 交易
    COMMENT = "comment"        # 评论
    MESSAGE = "message"        # 私信
    FAVORITE = "favorite"      # 收藏
    REPORT = "report"          # 举报

# ============================================
# 所有权检查器配置（策略模式）
# ============================================
# 为每种资源类型定义所有权检查逻辑
OWNERSHIP_CHECKERS: Dict[ResourceType, Callable] = {}

def register_ownership_checker(resource_type: ResourceType):
    """
    所有权检查器注册装饰器
    
    使用策略模式,为不同资源类型注册不同的检查逻辑
    """
    def decorator(func):
        OWNERSHIP_CHECKERS[resource_type] = func
        return func
    return decorator

# 为Item注册所有权检查器
@register_ownership_checker(ResourceType.ITEM)
def check_item_ownership(session: Session, resource_id: int, user_id: int) -> bool:
    """
    检查零件所有权
    
    规则: item.seller_id == user_id
    """
    item = session.get(Item, resource_id)
    if not item:
        return False
    return item.seller_id == user_id

# 为Transaction注册所有权检查器
@register_ownership_checker(ResourceType.TRANSACTION)
def check_transaction_ownership(session: Session, resource_id: int, user_id: int) -> bool:
    """
    检查交易参与权
    
    规则: tx.buyer_id == user_id OR tx.seller_id == user_id
    （采购商和供应商都可以查看交易）
    """
    tx = session.get(Transaction, resource_id)
    if not tx:
        return False
    return tx.buyer_id == user_id or tx.seller_id == user_id

# 为Comment注册所有权检查器

# 通用所有权检查依赖（工厂函数）
# ============================================
def check_ownership(resource_type: ResourceType, allow_admin: bool = True):
    """
    检查资源所有权（工厂函数）
    
    返回一个FastAPI依赖函数,检查当前用户是否拥有指定资源
    
    参数:
        resource_type: 资源类型（item/transaction/comment等）
        allow_admin: 是否允许管理员访问所有资源（默认True）
    
    返回:
        依赖函数: 检查所有权并返回资源对象
    
    使用示例:
        @router.put("/items/{item_id}")
        async def edit_item(
            item_id: int,
            item: Item = Depends(check_ownership(ResourceType.ITEM))
        ):
            # item变量是已验证所有权的零件对象
            ...
    
    实现原理:
    1. 工厂函数根据resource_type创建专门的检查函数
    2. 检查函数作为FastAPI依赖注入到路由
    3. 检查函数查询数据库验证所有权
    4. 验证通过返回资源对象,失败抛出403异常
    """
    
    async def ownership_checker(
        resource_id: int,
        current_user: User = Depends(get_current_user)
    ):
        """
        所有权检查依赖函数
        
        参数:
            resource_id: 资源ID（从路径参数提取）
            current_user: 当前用户（由get_current_user依赖注入）
        
        返回:
            资源对象（验证通过）
        
        异常:
            HTTPException 404: 资源不存在
            HTTPException 403: 无权访问该资源
        """
        
        # 管理员跳过所有权检查（可以访问所有资源）
        if allow_admin and current_user.is_superuser:
            # 直接返回资源（无需检查所有权）
            with db_manager.session_scope("mysql") as session:
                resource = get_resource_by_type(session, resource_type, resource_id)
                if not resource:
                    raise HTTPException(
                        status_code=status.HTTP_404_NOT_FOUND,
                        detail=f"{resource_type.value.capitalize()} not found"
                    )
            return resource
        
        # 查询资源并检查所有权
        with db_manager.session_scope("mysql") as session:
            # 获取对应资源类型的检查器
            checker = OWNERSHIP_CHECKERS.get(resource_type)
            if not checker:
                logger.error(f"No ownership checker registered for {resource_type}")
                raise HTTPException(
                    status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
                    detail="Ownership check not implemented"
                )
            
            # 执行所有权检查
            has_ownership = checker(session, resource_id, current_user.id)
            
            if not has_ownership:
                # 记录权限拒绝日志（安全审计）
                logger.warning(
                    f"Ownership check failed: user {current_user.username} "
                    f"tried to access {resource_type.value} {resource_id}"
                )
                raise HTTPException(
                    status_code=status.HTTP_403_FORBIDDEN,
                    detail=f"You don't have access to this {resource_type.value}"
                )
            
            # 返回资源对象（给路由处理函数使用）
            resource = get_resource_by_type(session, resource_type, resource_id)
            
            logger.info(
                f"Ownership check passed: user {current_user.username} "
                f"accessed {resource_type.value} {resource_id}"
            )
            
            return resource
    
    return ownership_checker

def get_resource_by_type(session: Session, resource_type: ResourceType, resource_id: int):
    """
    根据资源类型查询资源对象
    
    参数:
        session: 数据库会话
        resource_type: 资源类型枚举
        resource_id: 资源ID
    
    返回:
        资源对象（ORM模型实例）

    model_mapping = {
        ResourceType.ITEM: Item,
        ResourceType.TRANSACTION: Transaction,
        ResourceType.COMMENT: Comment,
        ResourceType.MESSAGE: Message,
        ResourceType.FAVORITE: Favorite,
        ResourceType.REPORT: Report,
    }
    
    model = model_mapping.get(resource_type)
    if not model:
        return None
    
    return session.get(model, resource_id)
```

```python
# core/security.py
from jose import JWTError, jwt
from passlib.context import CryptContext
from datetime import datetime, timedelta

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def create_access_token(data: dict, expires_delta: timedelta = None):
    """创建访问令牌"""
    
    to_encode = data.copy()
    
    if expires_delta:
        expire = datetime.utcnow() + expires_delta
    else:
        expire = datetime.utcnow() + timedelta(minutes=15)
    
    to_encode.update({"exp": expire, "iat": datetime.utcnow()})
    
    encoded_jwt = jwt.encode(
        to_encode, 
        settings.SECRET_KEY, 
        algorithm=settings.ALGORITHM
    )
    
    return encoded_jwt

def verify_password(plain_password: str, hashed_password: str) -> bool:
    """验证密码"""
    return pwd_context.verify(plain_password, hashed_password)

def get_password_hash(password: str) -> str:
    """密码哈希"""
    return pwd_context.hash(password)

# 登录接口
@router.post("/auth/login")
async def login(credentials: LoginRequest):
    """用户登录"""
    
    with db_manager.session_scope("mysql") as session:
        user = session.execute(
            select(User).where(User.username == credentials.username)
        ).scalar_one_or_none()
        
        if not user or not verify_password(credentials.password, user.password_hash):
            raise HTTPException(
                status_code=status.HTTP_401_UNAUTHORIZED,
                detail="Incorrect username or password"
            )
        
        if not user.is_active:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="Account is disabled"
            )
        
        # 创建访问令牌
        access_token = create_access_token(
            data={"sub": str(user.id), "username": user.username},
            expires_delta=timedelta(days=7)
        )
        
        # 创建刷新令牌
        refresh_token = create_access_token(
            data={"sub": str(user.id), "type": "refresh"},
            expires_delta=timedelta(days=30)
        )
        
        # 更新最后登录时间
        user.last_login_at = datetime.utcnow()
        session.commit()
        
        # 记录审计日志
        log_audit(user.id, "LOGIN", "auth", user.id, "User logged in")
    
    return {
        "access_token": access_token,
        "refresh_token": refresh_token,
        "token_type": "bearer",
        "expires_in": 604800  # 7天
    }
```

```python
@router.post("/auth/refresh")
async def refresh_token(refresh_request: RefreshTokenRequest):
    """刷新访问令牌"""
    
    try:
        payload = jwt.decode(
            refresh_request.refresh_token,
            settings.SECRET_KEY,
            algorithms=[settings.ALGORITHM]
        )
        
        if payload.get("type") != "refresh":
            raise HTTPException(status_code=401, detail="Invalid token type")
        
        user_id = int(payload.get("sub"))
        
        # 验证用户状态
        with db_manager.session_scope("mysql") as session:
            user = session.get(User, user_id)
            if not user or not user.is_active:
                raise HTTPException(status_code=401, detail="User not found or inactive")
        
        # 创建新的访问令牌
        new_access_token = create_access_token(
            data={"sub": str(user_id), "username": user.username},
            expires_delta=timedelta(days=7)
        )
        
        return {
            "access_token": new_access_token,
            "token_type": "bearer"
        }
        
    except JWTError:
        raise HTTPException(status_code=401, detail="Invalid refresh token")
```

```python
class DataEncryption:
    """数据加密工具"""
    
    def __init__(self, key: bytes):
        self.cipher = Fernet(key)
```

```python
            current_user = kwargs.get('current_user')
            request = kwargs.get('request')
            
            # 执行原函数

                    details=json.dumps(kwargs),
                    ip_address=request.client.host if request else None,
                    created_at=datetime.utcnow()
                )
                session.add(log)
                session.commit()
            
            return result
```
