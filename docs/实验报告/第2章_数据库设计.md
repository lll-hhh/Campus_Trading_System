# 第2章 数据库设计

## 2.1 概念结构设计

### 2.1.1 实体识别

根据需求分析，本系统包含以下核心实体：

#### 1. 用户实体（User）

**实体描述：** 系统的使用者，包括买家、卖家、管理员等角色。

**主要属性：**
- 用户ID（主键）
- 用户名
- 邮箱（校园邮箱）
- 学号
- 密码哈希
- 手机号
- 头像URL
- 真实姓名
- 账号状态（激活/冻结/封禁）
- 实名认证状态
- 信用评分
- 卖家评分
- 买家评分
- 总销售数
- 总购买数
- 注册时间
- 最后登录时间
- 同步版本号

**业务规则：**
- 用户名、邮箱、学号必须唯一
- 邮箱必须是校园邮箱（@*.edu.cn）
- 信用评分范围0-100，默认100
- 评分范围0-5，默认5.0

#### 2. 角色实体（Role）

**实体描述：** 用户角色，用于权限管理（RBAC）。

**主要属性：**
- 角色ID（主键）
- 角色名称（唯一）
- 角色描述
- 创建时间
- 更新时间
- 同步版本号

**典型角色：**
- 超级管理员（super_admin）
- 管理员（admin）
- 普通用户（user）
- 访客（guest）

#### 3. 权限实体（Permission）

**实体描述：** 系统权限，定义可执行的操作。

**主要属性：**
- 权限ID（主键）
- 权限名称（唯一）
- 资源类型
- 操作类型
- 权限描述
- 创建时间
- 更新时间
- 同步版本号

**权限示例：**
- user:create - 创建用户
- item:read - 查看商品
- item:update - 修改商品
- transaction:manage - 管理交易

#### 4. 商品分类实体（Category）

**实体描述：** 商品的分类体系。

**主要属性：**
- 分类ID（主键）
- 分类名称
- 分类标识（slug）
- 分类描述
- 图标
- 排序顺序
- 激活状态
- 创建时间
- 更新时间
- 同步版本号

**分类示例：**
- 图书教材
- 电子产品
- 生活用品
- 交通工具
- 其他

#### 5. 商品实体（Item）

**实体描述：** 用户发布的二手商品。

**主要属性：**
- 商品ID（主键）
- 卖家ID（外键）
- 分类ID（外键）
- 商品标题
- 商品描述
- 价格
- 原价
- 成色（全新/99新/95新/9成新/二手）
- 交易地点
- 联系方式（加密）
- 商品标签（JSON）
- 商品状态（在售/预定/已售/已删除）
- 是否可议价
- 是否包邮
- 浏览量
- 收藏量
- 咨询量
- 创建时间
- 更新时间
- 售出时间
- 同步版本号

**业务规则：**
- 价格必须大于0
- 商品状态流转：在售→预定→已售
- 已售商品不可修改
- 删除为软删除

#### 6. 商品图片实体（ItemImage）

**实体描述：** 商品的图片信息。

**主要属性：**
- 图片ID（主键）
- 商品ID（外键）
- 图片URL
- 排序顺序
- 是否封面
- 创建时间
- 更新时间
- 同步版本号

**业务规则：**
- 每个商品最多9张图片
- 必须有且仅有一张封面图
- 图片按排序顺序展示

#### 7. 交易实体（Transaction）

**实体描述：** 买卖双方的交易记录。

**主要属性：**
- 交易ID（主键）
- 商品ID（外键）
- 买家ID（外键）
- 卖家ID（外键）
- 商品价格
- 最终成交价
- 交易状态（待联系/已联系/约见中/已完成/已取消）
- 买家联系方式（加密）
- 卖家联系方式（加密）
- 约定见面地点
- 约定见面时间
- 买家评分
- 卖家评分
- 买家评价
- 卖家评价
- 创建时间
- 联系时间
- 完成时间
- 取消时间
- 同步版本号

**状态流转：**
```
待联系 → 已联系 → 约见中 → 已完成
   ↓        ↓         ↓
 已取消   已取消    已取消
```

#### 8. 评论实体（Comment）

**实体描述：** 用户对商品的评论。

**主要属性：**
- 评论ID（主键）
- 商品ID（外键）
- 用户ID（外键）
- 父评论ID（外键，用于回复）
- 评论内容
- 是否删除
- 是否被举报
- 创建时间
- 更新时间
- 同步版本号

**业务规则：**
- 支持二级评论（回复）
- 评论为软删除
- 被举报的评论需审核

#### 9. 消息实体（Message）

**实体描述：** 用户之间的私信。

**主要属性：**
- 消息ID（主键）
- 发送者ID（外键）
- 接收者ID（外键）
- 关联商品ID（外键，可选）
- 消息内容
- 是否已读
- 发送者删除标记
- 接收者删除标记
- 创建时间
- 更新时间
- 阅读时间
- 同步版本号

**业务规则：**
- 支持双向删除（软删除）
- 未读消息需要提醒
- 可关联具体商品

#### 10. 收藏实体（Favorite）

**实体描述：** 用户收藏的商品。

**主要属性：**
- 收藏ID（主键）
- 用户ID（外键）
- 商品ID（外键）
- 创建时间
- 更新时间
- 同步版本号

**业务规则：**
- 用户和商品组合唯一
- 商品删除时自动取消收藏
- 支持降价提醒

#### 11. 举报实体（Report）

**实体描述：** 用户举报记录。

**主要属性：**
- 举报ID（主键）
- 举报人ID（外键）
- 被举报用户ID（外键）
- 被举报商品ID（外键）
- 被举报评论ID（外键）
- 举报类型（诈骗/虚假商品/骚扰/垃圾信息/其他）
- 举报原因
- 处理状态（待处理/处理中/已解决/已驳回）
- 管理员备注
- 创建时间
- 更新时间
- 处理完成时间
- 同步版本号

**业务规则：**
- 举报对象至少有一个（用户/商品/评论）
- 处理完成后不可修改

#### 12. 审计日志实体（AuditLog）

**实体描述：** 系统操作审计记录。

**主要属性：**
- 日志ID（主键）
- 用户ID（外键）
- 操作类型（登录/创建/更新/删除等）
- 目标表名
- 目标记录ID
- 操作前数据（JSON）
- 操作后数据（JSON）
- IP地址
- User Agent
- 创建时间
- 同步版本号

**用途：**
- 安全审计
- 操作追溯
- 数据恢复参考

#### 13. 冲突记录实体（ConflictRecord）

**实体描述：** 数据库同步冲突记录。⭐

**主要属性：**
- 冲突ID（主键）
- 表名
- 记录ID
- 源数据库
- 目标数据库
- 冲突类型（版本冲突/删除冲突/约束冲突）
- 源数据（JSON）
- 目标数据（JSON）
- 冲突状态（待处理/已解决/已忽略）
- 解决方式（选择源/选择目标/手动合并）
- 管理员ID
- 创建时间
- 解决时间
- 同步版本号

**业务规则：**
- 自动检测版本冲突
- 邮件通知管理员
- 记录解决历史

#### 14. 同步配置实体（SyncConfig）

**实体描述：** 数据库同步配置。⭐

**主要属性：**
- 配置ID（主键）
- 表名
- 源数据库
- 目标数据库列表（JSON）
- 同步类型（实时/周期）
- 同步间隔（秒）
- 是否启用
- 最后同步时间
- 创建时间
- 更新时间
- 同步版本号

**用途：**
- 控制同步行为
- 配置同步策略
- 监控同步状态

#### 15. 同步日志实体（SyncLog）

**实体描述：** 数据库同步执行日志。⭐

**主要属性：**
- 日志ID（主键）
- 表名
- 源数据库
- 目标数据库
- 同步记录数
- 成功数
- 失败数
- 冲突数
- 执行状态（成功/失败/部分成功）
- 错误信息（JSON）
- 开始时间
- 结束时间
- 执行耗时（毫秒）
- 同步版本号

**用途：**
- 同步历史追踪
- 性能分析
- 故障排查

### 2.1.2 实体关系（E-R图）

#### 1. 用户相关关系

**用户 - 角色 关系（多对多）**
- 一个用户可以拥有多个角色
- 一个角色可以分配给多个用户
- 通过 user_roles 关联表实现

**角色 - 权限 关系（多对多）**
- 一个角色可以拥有多个权限
- 一个权限可以分配给多个角色
- 通过 role_permissions 关联表实现

**用户 - 用户资料 关系（一对一）**
- 一个用户对应一份详细资料
- 扩展用户基本信息

#### 2. 商品相关关系

**用户 - 商品 关系（一对多）**
- 一个用户（卖家）可以发布多个商品
- 一个商品只属于一个卖家
- 关系类型：发布

**分类 - 商品 关系（一对多）**
- 一个分类下可以有多个商品
- 一个商品属于一个分类
- 关系类型：归属

**商品 - 商品图片 关系（一对多）**
- 一个商品可以有多张图片（最多9张）
- 一张图片只属于一个商品
- 关系类型：包含

**用户 - 商品 关系（多对多 - 收藏）**
- 一个用户可以收藏多个商品
- 一个商品可以被多个用户收藏
- 通过 favorites 表实现

## 2.2 逻辑结构设计

### 2.2.1 关系模式转换

根据E-R图，将概念模型转换为关系模式。下面列出30张表的关系模式：

#### 1. 核心业务表（9张）

**users（用户表）**
```
users(
  id,                    -- PK
  username,              -- UNIQUE, NOT NULL
  email,                 -- UNIQUE, NOT NULL
  student_id,            -- UNIQUE
  password_hash,         -- NOT NULL
  phone,
  avatar_url,
  real_name,
  is_active,             -- DEFAULT TRUE
  is_verified,           -- DEFAULT FALSE
  is_banned,             -- DEFAULT FALSE
  credit_score,          -- DEFAULT 100
  seller_rating,         -- DEFAULT 5.00
  buyer_rating,          -- DEFAULT 5.00
  total_sales,           -- DEFAULT 0
  total_purchases,       -- DEFAULT 0
  created_at,
  updated_at,
  last_login_at,
  sync_version           -- DEFAULT 0
)
```

**categories（商品分类表）**
```
categories(
  id,                    -- PK
  name,                  -- NOT NULL
  slug,                  -- UNIQUE, NOT NULL
  description,
  icon,
  sort_order,            -- DEFAULT 0
  is_active,             -- DEFAULT TRUE
  created_at,
  updated_at,
  sync_version
)
```

**items（商品表）**
```
items(
  id,                    -- PK
  seller_id,             -- FK → users(id), NOT NULL
  category_id,           -- FK → categories(id)
  title,                 -- NOT NULL
  description,
  price,                 -- NOT NULL
  original_price,
  condition_type,        -- ENUM, DEFAULT '二手'
  location,
  contact_info,
  tags,                  -- JSON
  status,                -- ENUM, DEFAULT 'available'
  is_negotiable,         -- DEFAULT FALSE
  is_shipped,            -- DEFAULT FALSE
  view_count,            -- DEFAULT 0
  favorite_count,        -- DEFAULT 0
  inquiry_count,         -- DEFAULT 0
  created_at,
  updated_at,
  sold_at,
  sync_version
)
```

**item_images（商品图片表）**
```
item_images(
  id,                    -- PK
  item_id,               -- FK → items(id), NOT NULL
  image_url,             -- NOT NULL
  sort_order,            -- DEFAULT 0
  is_cover,              -- DEFAULT FALSE
  created_at,
  updated_at,
  sync_version
)
```

**comments（评论表）**
```
comments(
  id,                    -- PK
  item_id,               -- FK → items(id), NOT NULL
  user_id,               -- FK → users(id), NOT NULL
  parent_id,             -- FK → comments(id), NULL
  content,               -- NOT NULL
  is_deleted,            -- DEFAULT FALSE
  is_reported,           -- DEFAULT FALSE
  created_at,
  updated_at,
  sync_version
)
```

**transactions（交易表）**
```
transactions(
  id,                    -- PK
  item_id,               -- FK → items(id), NOT NULL
  buyer_id,              -- FK → users(id), NOT NULL
  seller_id,             -- FK → users(id), NOT NULL
  item_price,            -- NOT NULL
  final_amount,          -- NOT NULL
  status,                -- ENUM, DEFAULT 'pending'
  buyer_contact,
  seller_contact,
  meeting_location,
  meeting_time,
  buyer_rating,          -- 1-5
  seller_rating,         -- 1-5
  buyer_review,
  seller_review,
  created_at,
  contacted_at,
  completed_at,
  cancelled_at,
  sync_version
)
```

**messages（消息表）**
```
messages(
  id,                    -- PK
  sender_id,             -- FK → users(id), NOT NULL
  receiver_id,           -- FK → users(id), NOT NULL
  item_id,               -- FK → items(id), NULL
  content,               -- NOT NULL
  is_read,               -- DEFAULT FALSE
  is_deleted_by_sender,  -- DEFAULT FALSE
  is_deleted_by_receiver,-- DEFAULT FALSE
  created_at,
  updated_at,
  read_at,
  sync_version
)
```

**favorites（收藏表）**
```
favorites(
  id,                    -- PK
  user_id,               -- FK → users(id), NOT NULL
  item_id,               -- FK → items(id), NOT NULL
  created_at,
  updated_at,
  sync_version,
  UNIQUE(user_id, item_id)
)
```

**reports（举报表）**
```
reports(
```

### 2.2.2 数据规范化分析

#### 第一范式（1NF）

**定义：** 表中的每个字段都是不可再分的原子值。

**本系统的实现：**

✅ **符合1NF的设计：**
- 所有表的字段都是原子值
- 用户信息（用户名、邮箱、手机）分开存储
- 时间字段独立（创建时间、更新时间）

⚠️ **使用JSON类型的字段：**
虽然JSON字段在物理上是复合类型，但在业务逻辑上作为整体使用，符合业务需求：
- `items.tags` - 商品标签数组，整体作为一个属性
- `system_configs.value` - 配置值，灵活存储不同类型配置
- `sync_logs.error_details` - 错误详情，便于记录复杂错误信息

**示例分析：**

❌ **不符合1NF（错误示例）：**
```sql
-- 联系方式字段包含多个值
CREATE TABLE users (
  contacts VARCHAR(500)  -- "手机:13800138000,邮箱:user@example.com"
);
```

✅ **符合1NF（正确设计）：**
```sql
CREATE TABLE users (
  phone VARCHAR(20),
  email VARCHAR(100)
);
```

#### 第二范式（2NF）

**定义：** 在1NF基础上，非主属性完全依赖于主键，不存在部分依赖。

**本系统的实现：**

✅ **消除部分依赖的设计：**

**示例1：商品图片表**
- 如果设计为 `(item_id, image_url)` 作为联合主键
- `sort_order` 和 `is_cover` 只依赖于完整的联合主键
- 采用单独的 `id` 作为主键，避免复杂依赖

**示例2：用户角色关联表**
```sql
-- 正确设计：使用独立主键
user_roles(
  id,           -- 独立主键
  user_id,      -- 完全依赖于id
  role_id,      -- 完全依赖于id
  created_at    -- 完全依赖于id
)

-- 而不是使用联合主键
-- PRIMARY KEY (user_id, role_id)
-- 这样created_at等字段完全依赖于整个主键
```

**不存在的部分依赖：**
- 所有表都使用单一主键（id），不使用复合主键
- 所有非主属性都完全依赖于主键

#### 第三范式（3NF）

**定义：** 在2NF基础上，消除传递依赖，非主属性不依赖于其他非主属性。

**本系统的实现：**

✅ **消除传递依赖的设计：**

**示例1：商品表优化**
```sql
-- 错误设计（存在传递依赖）：
items(
  id,
  seller_id,
  seller_name,      -- 依赖于seller_id
  seller_email,     -- 依赖于seller_id
  category_id,
  category_name,    -- 依赖于category_id
  ...
)

-- 正确设计（符合3NF）：
items(
  id,
  seller_id,        -- 通过外键关联users表
  category_id,      -- 通过外键关联categories表
  ...
)

users(id, username, email, ...)
categories(id, name, ...)
```

**示例2：交易表优化**
```sql
-- 正确设计
transactions(
  id,
  item_id,          -- 关联商品
  buyer_id,         -- 关联买家
  seller_id,        -- 关联卖家
  item_price,       -- 商品价格（冗余，但符合业务需求）
  final_amount,     -- 最终成交价
  ...
)

-- item_price 是冗余字段，但因为商品价格可能变化
-- 保存交易时的价格是业务需要，属于合理的反规范化
```

**合理的反规范化：**

为提升查询性能，某些字段进行了合理的反规范化：

1. **items表的统计字段**
   ```sql
   view_count,        -- 浏览量（避免COUNT查询）
   favorite_count,    -- 收藏量（避免JOIN统计）
   inquiry_count      -- 咨询量
   ```

2. **users表的统计字段**
   ```sql
   total_sales,       -- 总销售数
   total_purchases,   -- 总购买数
   seller_rating,     -- 卖家评分
   buyer_rating       -- 买家评分
   ```

3. **conversations表的冗余字段**
   ```sql
   last_message_content,  -- 最后消息内容（避免JOIN messages表）
   last_message_at,       -- 最后消息时间
   user1_unread_count,    -- 未读数量（避免COUNT查询）
   user2_unread_count
   ```

**反规范化说明：**
这些冗余字段通过触发器或应用层逻辑保持同步，在性能和规范性之间取得平衡。

#### BCNF（Boyce-Codd范式）

**定义：** 在3NF基础上，每个决定因素都是候选键。

**本系统的分析：**

✅ **符合BCNF的设计：**

本系统的所有表都符合BCNF，因为：
1. 所有表使用单一主键（id）
2. 所有函数依赖的决定因素都是主键
3. 不存在非平凡的函数依赖其决定因素不是候选键的情况

**唯一约束分析：**
```sql
-- users表
UNIQUE(username)     -- username → 所有其他属性
UNIQUE(email)        -- email → 所有其他属性
UNIQUE(student_id)   -- student_id → 所有其他属性

-- 这些都是候选键，符合BCNF
```

## 2.3 物理结构设计

### 2.3.1 存储引擎选择

#### MySQL/MariaDB存储引擎

**选用 InnoDB 引擎，理由如下：**

1. **事务支持（ACID）**
   - 完整的事务支持
   - 支持提交、回滚
   - 适合金融交易场景

2. **行级锁**
   - 并发性能好
   - 支持高并发写入
   - 减少锁竞争

3. **外键支持**
   - 虽然应用层维护外键
   - 但InnoDB提供了外键机制备用

4. **崩溃恢复**
   - 自动崩溃恢复
   - 数据安全性高

5. **缓存机制**
   - 缓冲池优化
   - 提高查询性能

**配置示例：**
```sql
CREATE TABLE items (
  ...
) ENGINE=InnoDB 
  DEFAULT CHARSET=utf8mb4 
  COLLATE=utf8mb4_unicode_ci
  ROW_FORMAT=DYNAMIC
  COMMENT='商品表';
```

#### PostgreSQL存储特性

PostgreSQL 不需要显式指定存储引擎，但具有以下优势：

1. **MVCC（多版本并发控制）**
   - 读写不阻塞
   - 高并发性能

2. **丰富的数据类型**
   - JSON/JSONB类型
   - 数组类型
   - 全文搜索类型

3. **强大的索引**
   - GIN索引（JSON）
   - GiST索引（全文搜索）
   - 部分索引

#### SQLite存储特性

1. **文件存储**
   - 单文件数据库
   - 便于备份和移动

2. **轻量级**
   - 适合开发和测试
   - 资源占用小

3. **嵌入式**
   - 无需服务器
   - 配置简单

### 2.3.2 索引设计

#### 索引设计原则

1. **主键索引**：所有表的id字段自动创建聚簇索引
2. **唯一索引**：唯一约束字段自动创建唯一索引
3. **外键索引**：外键字段创建普通索引
4. **查询优化索引**：根据常用查询创建复合索引
5. **全文索引**：文本搜索字段创建全文索引

#### 详细索引列表

**users表索引：**
```sql
PRIMARY KEY (id)                           -- 主键索引
```

```sql
CREATE TABLE conflict_records (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '冲突ID',
    table_name VARCHAR(100) NOT NULL COMMENT '表名',
    record_id VARCHAR(50) NOT NULL COMMENT '记录ID',
    source_db VARCHAR(50) NOT NULL COMMENT '源数据库',
    target_db VARCHAR(50) NOT NULL COMMENT '目标数据库',
    conflict_type ENUM('version', 'delete', 'constraint') COMMENT '冲突类型',
    source_data JSON COMMENT '源数据(JSON)',
    target_data JSON COMMENT '目标数据(JSON)',
    status ENUM('pending', 'resolved', 'ignored') 
        DEFAULT 'pending' COMMENT '冲突状态',
    resolution ENUM('keep_source', 'keep_target', 'manual') COMMENT '解决方式',
    resolved_by BIGINT COMMENT '解决人ID',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '发现时间',
    resolved_at TIMESTAMP NULL COMMENT '解决时间',
    sync_version INT DEFAULT 0,
    
    INDEX idx_table (table_name),
    INDEX idx_status (status),
    INDEX idx_created (created_at),
    INDEX idx_source_target (source_db, target_db),
    INDEX idx_table_status (table_name, status),
    
    FOREIGN KEY (resolved_by) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='冲突记录表';
```

**冲突类型说明：**

| 类型 | 英文 | 说明 | 示例 |
|-----|------|------|------|
| 版本冲突 | version | 同一记录在不同数据库被同时修改 | sync_version不一致 |
| 删除冲突 | delete | 一边修改一边删除 | 记录已不存在 |
| 约束冲突 | constraint | 违反约束条件 | 外键不存在 |

**解决方式：**
- `keep_source`: 保留源数据库的值
- `keep_target`: 保留目标数据库的值
- `manual`: 手动合并

**示例数据：**


#### sync_logs表（同步日志表）⭐

**表用途：** 记录每次数据库同步任务的执行情况。

**建表语句（MySQL）：**
```sql
CREATE TABLE sync_logs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '日志ID',
    table_name VARCHAR(100) NOT NULL COMMENT '表名',
    source_db VARCHAR(50) NOT NULL COMMENT '源数据库',
    target_db VARCHAR(50) NOT NULL COMMENT '目标数据库',
    records_synced INT DEFAULT 0 COMMENT '同步记录数',
    records_success INT DEFAULT 0 COMMENT '成功数',
    records_failed INT DEFAULT 0 COMMENT '失败数',
    conflicts_detected INT DEFAULT 0 COMMENT '冲突数',
    status ENUM('success', 'failed', 'partial') COMMENT '执行状态',
    error_details JSON COMMENT '错误详情(JSON)',
    started_at TIMESTAMP NOT NULL COMMENT '开始时间',
    finished_at TIMESTAMP NULL COMMENT '结束时间',
    duration_ms INT COMMENT '执行耗时(毫秒)',
    sync_version INT DEFAULT 0,
    
    INDEX idx_table (table_name),
    INDEX idx_source_target (source_db, target_db),
    INDEX idx_started (started_at),
    INDEX idx_status (status),
    INDEX idx_table_started (table_name, started_at DESC)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='同步日志表';
```

**统计指标：**
```sql
-- 同步成功率
SELECT 
    table_name,
    COUNT(*) as total_syncs,
    SUM(CASE WHEN status = 'success' THEN 1 ELSE 0 END) as success_count,
    ROUND(SUM(CASE WHEN status = 'success' THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) as success_rate,
    AVG(duration_ms) as avg_duration_ms
FROM sync_logs
WHERE started_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY table_name;
```

### 2.5.2 数据库差异处理

不同数据库的SQL语法差异及处理：

**AUTO_INCREMENT差异：**
```sql
-- MySQL/MariaDB
id BIGINT PRIMARY KEY AUTO_INCREMENT

-- PostgreSQL
id BIGSERIAL PRIMARY KEY
-- 或
id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY

-- SQLite
id INTEGER PRIMARY KEY AUTOINCREMENT
```

**JSON类型差异：**
```sql
-- MySQL
tags JSON

-- PostgreSQL
tags JSONB  -- 推荐使用JSONB，性能更好

-- SQLite
tags TEXT  -- 存储为文本
```

**ENUM类型差异：**
```sql
-- MySQL
status ENUM('pending', 'completed', 'cancelled')

-- PostgreSQL
-- 需要先创建类型
CREATE TYPE status_type AS ENUM('pending', 'completed', 'cancelled');
status status_type

-- SQLite (使用CHECK约束)
status TEXT CHECK(status IN ('pending', 'completed', 'cancelled'))
```

**时间戳差异：**
```sql
-- MySQL
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

-- PostgreSQL
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
-- 需要触发器实现ON UPDATE

-- SQLite
created_at DATETIME DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
-- 需要触发器实现ON UPDATE
```
