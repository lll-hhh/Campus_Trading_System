# 第2章 数据库设计

## 2.1 概念结构设计

### 2.1.1 实体识别

根据需求分析，本系统包含以下核心实体：

#### 1. 用户实体（User）

**实体描述：** 用户是系统的核心实体，代表所有注册用户，包括买家、卖家、管理员等不同角色。用户实体存储了用户的基本信息、认证信息、信用评分、交易统计等完整的用户画像数据。每个用户通过唯一的用户ID标识，邮箱和用户名也具有唯一性约束确保不会重复注册。用户实体与角色、商品、交易、消息等多个实体建立关联，是整个系统的中心节点。

**主要属性：**
- **用户ID（主键）**：自增整数，唯一标识每个用户，作为主键索引，所有关联表通过此ID建立外键关系
- **用户名**：字符串类型（VARCHAR 50），唯一约束，用于登录和展示，要求3-20个字符，只能包含字母、数字、下划线
- **邮箱（校园邮箱）**：字符串类型（VARCHAR 100），唯一约束，必须是@*.edu.cn格式的校园邮箱，用于账号激活、找回密码、重要通知
- **学号**：字符串类型（VARCHAR 50），唯一约束，用于校园身份验证和实名认证，格式如"2021001234"
- **密码哈希**：字符串类型（VARCHAR 255），存储bcrypt加密后的密码哈希值（60字符），加盐迭代12轮，永不存储明文密码
- **手机号**：字符串类型（VARCHAR 20），可空，用于短信验证和联系，格式如"13800138000"
- **头像URL**：字符串类型（VARCHAR 255），可空，存储头像图片的URL地址，默认使用系统默认头像
- **真实姓名**：字符串类型（VARCHAR 50），可空，实名认证后填写，用于高价值交易的身份确认
- **账号状态**：枚举类型（ENUM: active/frozen/banned），默认active激活状态，frozen冻结状态可恢复，banned封禁状态永久禁用
- **实名认证状态**：布尔类型（BOOLEAN），默认false未认证，认证通过后为true，认证用户享有更高权限和信用度
- **信用评分**：整数类型（INT），范围0-1000，默认800，综合成交次数、好评率、违规记录等因素计算，分数越高信用越好
- **卖家评分**：浮点类型（DECIMAL 3,2），范围0-5.0，默认5.0，基于买家评价计算的卖家服务评分，保留两位小数
- **买家评分**：浮点类型（DECIMAL 3,2），范围0-5.0，默认5.0，基于卖家评价计算的买家信用评分，保留两位小数
- **总销售数**：整数类型（INT），默认0，累计成功售出的商品数量，用于计算卖家活跃度
- **总购买数**：整数类型（INT），默认0，累计成功购买的商品数量，用于计算买家活跃度
- **注册时间**：日期时间类型（DATETIME），记录用户首次注册的时间戳，不可修改
- **最后登录时间**：日期时间类型（DATETIME），记录用户最近一次登录的时间戳，每次登录自动更新
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步的乐观锁版本控制，每次修改自动递增

**业务规则：**
- **唯一性约束：** 用户名、邮箱、学号三个字段必须全局唯一，注册时需检查是否已被使用，建立唯一索引加速查询和防止重复
- **邮箱格式验证：** 邮箱必须匹配正则表达式`^[a-zA-Z0-9._-]+@[a-zA-Z0-9.-]+\.edu\.cn$`，确保是校园邮箱，非教育邮箱无法注册
- **信用评分机制：** 信用评分范围0-1000分，新用户默认800分（中等信用），成功交易+5分，好评+10分，差评-20分，违规-100分，分数低于500分会被限制发布商品
- **评分计算公式：** 卖家/买家评分 = 所有评价分数之和 ÷ 评价总数，范围0-5.0保留两位小数，如卖家收到10个评价（5,5,5,4,5,5,4,5,5,5）则评分为4.80
- **统计数据更新：** 总销售数和总购买数在交易完成（status=completed）时通过触发器自动更新，不可手动修改，确保数据准确性

#### 2. 角色实体（Role）

**实体描述：** 角色实体是RBAC（基于角色的访问控制）权限体系的核心组件，定义了系统中的各种用户角色类型。每个角色关联一组权限，用户通过分配角色来获得相应的系统操作权限。采用角色管理可以简化权限分配，批量管理用户权限，符合最小权限原则和职责分离原则。系统预置了4种基础角色，管理员可以根据需要创建自定义角色。

**主要属性：**
- **角色ID（主键）**：自增整数，唯一标识每个角色，作为role_permissions中间表的外键
- **角色名称（唯一）**：字符串类型（VARCHAR 50），唯一约束，角色的标识符如"admin"、"user"，全局唯一不可重复
- **角色描述**：文本类型（TEXT），角色的详细说明，描述该角色的职责和权限范围，如"系统管理员，拥有所有权限"
- **创建时间**：日期时间类型（DATETIME），记录角色创建的时间戳
- **更新时间**：日期时间类型（DATETIME），记录角色最后修改的时间戳，修改时自动更新
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步的版本控制

**典型角色：**
- **超级管理员（super_admin）**：拥有系统所有权限，可以管理用户、角色、权限、系统配置等，通常只有1-2个超级管理员账号，权限不可被修改或删除
- **管理员（admin）**：拥有日常运营管理权限，可以审核商品、处理举报、查看报表、封禁用户，但不能修改系统权限配置
- **普通用户（user）**：默认角色，拥有基本功能权限，可以浏览商品、发布商品、购买商品、发送消息、收藏商品等常规操作
- **访客（guest）**：未登录用户或受限用户，只能浏览公开信息（商品列表、商品详情），不能发布商品、下单购买、发送消息

**业务规则：**
- **角色名称唯一性：** 角色名称必须全局唯一，使用英文小写加下划线命名（如user_vip），方便代码中引用
- **预置角色保护：** 系统的4个预置角色（super_admin、admin、user、guest）不允许删除，防止权限体系崩溃
- **角色继承关系：** 虽然数据库表未直接实现继承，但权限设计上遵循继承原则，高级角色包含低级角色的所有权限（super_admin > admin > user > guest）
- **角色分配规则：** 一个用户可以拥有多个角色（多对多关系，通过user_roles中间表实现），用户的最终权限是所有角色权限的并集

#### 3. 权限实体（Permission）

**实体描述：** 权限实体定义了系统中所有可执行的操作，采用"资源:操作"的命名模式（如item:create、user:delete），粒度细化到具体的资源和操作类型。权限通过角色进行分组和分配，遵循RBAC模型，实现了灵活且安全的权限管理。系统预置了50+个基础权限，覆盖用户管理、商品管理、交易管理、系统管理等各个模块，管理员可以根据业务需求添加自定义权限。

**主要属性：**
- **权限ID（主键）**：自增整数，唯一标识每个权限
- **权限名称（唯一）**：字符串类型（VARCHAR 100），唯一约束，权限的标识符，格式为"资源:操作"如"item:update"，全局唯一
- **资源类型**：字符串类型（VARCHAR 50），表示权限作用的资源类型，如"user"（用户）、"item"（商品）、"transaction"（交易）、"system"（系统设置）
- **操作类型**：字符串类型（VARCHAR 50），表示对资源的操作，如"create"（创建）、"read"（读取）、"update"（修改）、"delete"（删除）、"manage"（管理）
- **权限描述**：文本类型（TEXT），权限的详细说明，描述该权限允许用户执行的具体操作，如"允许用户修改自己发布的商品信息"
- **创建时间**：日期时间类型（DATETIME），记录权限创建的时间戳
- **更新时间**：日期时间类型（DATETIME），记录权限最后修改的时间戳
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步的版本控制

**权限示例：**
- **user:create**：创建用户权限，允许注册新用户或管理员添加用户，通常开放给所有人（注册）或仅管理员（后台创建）
- **item:read**：查看商品权限，允许浏览商品列表和商品详情，开放给所有用户包括未登录用户
- **item:create**：发布商品权限，允许用户发布新商品，要求用户已登录且通过邮箱验证，高价值商品可能要求实名认证
- **item:update**：修改商品权限，允许用户修改自己发布的商品信息（标题、价格、描述、图片等），不能修改他人商品
- **item:delete**：删除商品权限，允许用户删除自己发布的商品（软删除），管理员可以删除任何违规商品
- **transaction:create**：创建交易权限，允许用户下单购买商品，要求用户已登录且账户余额充足
- **transaction:manage**：管理交易权限，允许管理员查看所有交易记录、处理纠纷、强制退款等高级操作
- **user:ban**：封禁用户权限，允许管理员封禁违规用户，仅限管理员角色拥有
- **report:handle**：处理举报权限，允许管理员查看和处理用户举报，标记处理结果
- **system:config**：系统配置权限，允许修改系统参数、查看敏感信息，仅限超级管理员

**业务规则：**
- **权限命名规范：** 权限名称必须遵循"资源:操作"格式，使用小写字母和冒号分隔，如"item:update"、"user:ban"，便于代码中统一处理
- **权限粒度控制：** 权限粒度要适中，既不能过粗（如一个权限控制整个模块）导致权限过大，也不能过细（如每个字段都是一个权限）导致管理复杂
- **权限检查机制：** API接口通过装饰器`@require_permission("item:delete")`进行权限检查，未授权的请求返回403 Forbidden错误
- **资源所有权验证：** 除了权限检查，还需验证资源所有权，如用户虽然有item:update权限，但只能修改自己发布的商品（seller_id=current_user.id），不能修改他人商品
- **权限继承规则：** manage权限通常包含create、read、update、delete四个基础权限，如transaction:manage隐含了transaction:read、transaction:update等

#### 4. 商品分类实体（Category）

**实体描述：** 商品分类实体定义了商品的分类体系，采用扁平化的一级分类设计（考虑到校园二手交易场景分类相对简单）。分类帮助用户快速定位商品，提高搜索效率，也便于平台进行商品管理和数据统计。每个分类都有独特的图标和颜色主题，提升用户体验。系统预置了8个核心分类，管理员可以根据需要动态添加、修改或停用分类。

**主要属性：**
- **分类ID（主键）**：自增整数，唯一标识每个分类，作为items表的外键
- **分类名称**：字符串类型（VARCHAR 50），分类的显示名称，如"图书教材"、"电子产品"、"生活用品"，简洁明了
- **分类标识（slug）**：字符串类型（VARCHAR 50），唯一约束，分类的URL友好标识符，如"books"、"electronics"、"daily-goods"，用于生成SEO友好的URL（如/category/electronics）
- **分类描述**：文本类型（TEXT），分类的详细说明，描述该分类包含的商品类型和适用范围，如"包括各学科教材、辅导书、考研资料、小说、杂志等"
- **图标**：字符串类型（VARCHAR 100），分类图标的CSS类名或图标URL，如"icon-book"、"fa fa-laptop"，用于前端显示
- **排序顺序**：整数类型（INT），默认0，控制分类在列表中的显示顺序，数字越小越靠前，支持拖拽排序
- **激活状态**：布尔类型（BOOLEAN），默认true激活，false表示停用，停用的分类不在前端显示但保留数据，已发布的商品不受影响
- **创建时间**：日期时间类型（DATETIME），记录分类创建的时间戳
- **更新时间**：日期时间类型（DATETIME），记录分类最后修改的时间戳
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步的版本控制

**分类示例：**
- **图书教材（Books）**：包括各学科教材、辅导书、考研资料、小说、杂志、漫画等，是校园二手交易的主力品类，占比约40%
- **电子产品（Electronics）**：包括手机、平板、电脑、相机、耳机、充电器、数据线、键盘鼠标等，高价值商品，要求卖家提供发票和保修
- **生活用品（Daily Goods）**：包括文具、台灯、收纳盒、床上用品、洗漱用品、护肤品、零食等日常生活用品
- **交通工具（Vehicles）**：包括自行车、电动车、滑板、平衡车等校园代步工具，需要注意交易地点和试骑验货
- **服装鞋帽（Clothing）**：包括衣服、裤子、鞋子、帽子、包包、配饰等，注意标注尺码、新旧程度、是否洗过
- **运动健身（Sports）**：包括运动器材、健身器械、球类、户外用品、运动服装、运动鞋等，强调功能性和安全性
- **美妆护肤（Beauty）**：包括化妆品、护肤品、香水、美容工具等，要求标注生产日期、保质期、是否开封
- **其他（Others）**：不属于以上分类的商品，如手工制品、艺术品、植物、宠物用品等小众品类

**业务规则：**
- **扁平化分类：** 采用一级分类而非多级嵌套，简化分类体系，降低用户认知成本，校园二手交易场景下一级分类已足够
- **分类图标主题：** 每个分类配有独特的图标和主题色，提升视觉识别度，如图书教材使用蓝色书本图标，电子产品使用灰色笔记本图标
- **排序规则：** 分类按sort_order字段升序排列，相同order按ID升序，管理员可以通过拖拽调整分类顺序，热门分类排在前面
- **停用而非删除：** 分类停用时设置is_active=false而不是物理删除，已发布的商品仍关联原分类，只是前端不再显示该分类入口
- **商品必选分类：** 发布商品时必须选择一个分类，不允许为空，确保所有商品都可以通过分类筛选找到
- **分类统计：** 定期统计每个分类的商品数量、成交量、成交额，识别热门分类和冷门分类，优化分类设置

#### 5. 商品实体（Item）

**实体描述：** 商品实体是系统的核心业务实体，代表用户发布的二手商品信息。包含商品的完整描述、价格、成色、状态等关键信息，是买卖双方交易的标的物。商品实体与用户、分类、图片、交易、评论、收藏等多个实体建立关联，构成完整的商品生命周期管理。每个商品都有状态流转（在售→预定→已售→归档），支持浏览统计、收藏功能、议价功能等增值服务。

**主要属性：**
- **商品ID（主键）**：自增整数，唯一标识每个商品，作为交易、评论、收藏等表的外键
- **卖家ID（外键）**：整数类型，关联users表，表示发布商品的卖家，索引字段用于查询某用户的所有商品
- **分类ID（外键）**：整数类型，关联categories表，表示商品所属分类，必填项，用于分类筛选和统计
- **商品标题**：字符串类型（VARCHAR 200），商品的简短标题，限制5-200字符，要求简洁明了突出卖点，如"iPhone 13 Pro 256G 石墨色 95新 三网通"
- **商品描述**：文本类型（TEXT），商品的详细描述，支持富文本格式（Markdown或HTML），最多5000字，建议包含商品来源、使用情况、瑕疵说明、购买原因、转手原因等详细信息
- **价格**：decimal类型（DECIMAL 10,2），商品当前售价，保留两位小数，必须>0，单位元，如199.99表示199元9角9分
- **原价**：decimal类型（DECIMAL 10,2），可空，商品购买时的原价，用于计算折扣率，展示性价比，如原价3999元现价1999元则折扣50%
- **成色**：枚举类型（ENUM），商品新旧程度，可选值：全新（brand_new，未拆封）、99新（like_new，开封未使用）、95新（excellent，使用1-2次）、9成新（good，轻度使用痕迹）、8成新（fair，正常使用痕迹）、7成新及以下（poor，明显磨损）
- **交易地点**：字符串类型（VARCHAR 200），建议的交易地点，如"北门星巴克"、"图书馆门口"、"宿舍楼下"，优先选择公共场所保证安全
- **联系方式（加密）**：字符串类型（VARCHAR 255），卖家的联系方式（手机号、微信号、QQ号），使用AES加密存储，仅买家付费或下单后可见，防止爬虫和骚扰
- **商品标签（JSON）**：JSON类型，商品的自定义标签数组，如["急售","包邮","可刀价","支持退换","全套配件"]，以JSON格式存储如`["急售","包邮"]`，方便筛选和展示
- **商品状态**：枚举类型（ENUM），商品当前状态，可选值：在售（available，正常展示可购买）、预定（reserved，已有买家预定暂不接受其他咨询）、已售（sold，交易完成不再展示）、已删除（deleted，软删除不显示但保留数据）
- **是否可议价**：布尔类型（BOOLEAN），默认true，表示价格可以商量，买家可以发起议价，false表示一口价不议价
- **是否包邮**：布尔类型（BOOLEAN），默认false，对于可邮寄的商品（如图书、小件物品），true表示卖家承担邮费
- **浏览量**：整数类型（INT），默认0，商品被查看的次数，每次打开详情页+1，通过Redis缓存批量更新数据库减轻压力
- **收藏量**：整数类型（INT），默认0，商品被收藏的次数，与favorites表的记录数保持一致，通过触发器自动更新
- **咨询量**：整数类型（INT），默认0，商品被咨询的次数（发送私信），反映商品热度和买家兴趣度
- **创建时间**：日期时间类型（DATETIME），商品发布的时间戳，用于排序（最新发布）和统计
- **更新时间**：日期时间类型（DATETIME），商品最后修改的时间戳，修改标题、价格、描述等信息时自动更新，影响排序权重
- **售出时间**：日期时间类型（DATETIME），可空，商品标记为已售的时间戳，用于统计成交周期（售出时间-创建时间）
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步的乐观锁版本控制

**业务规则：**
- **价格验证：** 价格必须大于0且小于999999（近100万元），过高价格需要管理员审核防止异常数据，小数点后最多两位
- **状态流转规则：** 商品状态只能按照 在售→预定→已售 的顺序流转，不能逆向流转（已售商品不能改回在售），状态变更记录到audit_logs表
- **已售商品保护：** 商品标记为已售后禁止修改标题、价格、描述等核心信息，只能添加评价，保证交易记录的真实性和可追溯性
- **软删除机制：** 用户删除商品时不会物理删除记录，而是将状态设置为deleted，保留30天后永久删除，期间可以恢复
- **标题关键词检测：** 商品标题自动检测敏感词（如"诈骗"、"假货"、"代考"），包含敏感词的商品自动下架并通知管理员审核
- **图片必填验证：** 发布商品时至少上传1张图片（item_images表至少有1条记录且is_cover=true），没有图片的商品无法发布
- **价格变动记录：** 商品价格每次修改都记录到price_history表（时间序列数据），展示价格走势图，防止恶意修改价格
- **浏览量防刷：** 同一IP或用户24小时内重复浏览同一商品只计数1次，通过Redis Set记录viewed:item:123:user:456，过期时间24小时

#### 6. 商品图片实体（ItemImage）

**实体描述：** 商品图片实体存储商品的多张图片信息，支持每个商品上传最多9张图片。图片按照排序顺序展示，其中一张标记为封面图用于列表展示。图片URL指向云存储（如阿里云OSS、腾讯云COS）的地址，支持多尺寸缩略图加速加载。

**主要属性：**
- **图片ID（主键）**：自增整数，唯一标识每张图片
- **商品ID（外键）**：整数类型，关联items表，表示图片所属的商品，索引字段，删除商品时级联删除图片
- **图片URL**：字符串类型（VARCHAR 500），图片的完整URL地址，如`https://cdn.example.com/items/123/image1.jpg`，支持CDN加速
- **排序顺序**：整数类型（INT），默认0，控制图片在商品详情页的显示顺序，数字越小越靠前，用户可以拖拽调整
- **是否封面**：布尔类型（BOOLEAN），默认false，标记是否为封面图，每个商品有且仅有一张封面图，封面图展示在列表页和分享卡片
- **创建时间**：日期时间类型（DATETIME），图片上传的时间戳
- **更新时间**：日期时间类型（DATETIME），图片信息最后修改的时间戳
- **同步版本号**：整数类型（INT），默认1，用于多数据库同步

**业务规则：**
- **数量限制：** 每个商品最多9张图片，超过限制时提示用户删除旧图片后再上传，通过CHECK约束或应用层验证实现
- **封面图唯一：** 每个商品必须有且仅有一张封面图（is_cover=true），设置新封面时自动取消原封面，通过触发器或应用逻辑保证
- **图片格式验证：** 仅支持JPG、PNG、WebP格式，文件大小<5MB，上传时自动压缩和裁剪，生成多个尺寸（原图、大图800px、中图400px、小图200px、缩略图100px）
- **排序自动调整：** 新上传的图片默认排在最后，用户拖拽调整顺序时重新计算所有图片的sort_order，保持连续递增
- **图片清理机制：** 商品删除30天后，图片从云存储中永久删除节省成本，删除前会备份到归档存储

#### 7. 交易实体（Transaction）

**实体描述：** 交易实体记录买卖双方的交易过程，从买家下单到交易完成的完整生命周期。包含交易状态、联系方式、见面时间地点、评分等信息。支持交易状态流转、双向评价、纠纷处理等功能。

**主要属性：**
- **交易ID（主键）**：自增整数，唯一标识每笔交易
- **商品ID（外键）**：整数类型，关联items表，表示交易的商品
- **买家ID（外键）**：整数类型，关联users表，表示购买方
- **卖家ID（外键）**：整数类型，关联users表，表示出售方，冗余存储避免关联items表
- **商品价格**：decimal类型（DECIMAL 10,2），商品的标价，记录交易时的价格快照，防止卖家修改价格
- **最终成交价**：decimal类型（DECIMAL 10,2），实际成交价格，可能低于标价（议价后的价格）
- **交易状态**：枚举类型（ENUM），可选值：待联系（pending）、已联系（contacted）、约见中（meeting）、已完成（completed）、已取消（cancelled）
- **买家联系方式（加密）**：字符串类型（VARCHAR 255），买家的联系方式，AES加密存储
- **卖家联系方式（加密）**：字符串类型（VARCHAR 255），卖家的联系方式，AES加密存储
- **约定见面地点**：字符串类型（VARCHAR 200），可空，双方约定的交易地点
- **约定见面时间**：日期时间类型（DATETIME），可空，双方约定的交易时间
- **买家评分**：整数类型（INT），范围1-5，买家对卖家的评分，交易完成后可填写
- **卖家评分**：整数类型（INT），范围1-5，卖家对买家的评分，交易完成后可填写
- **买家评价**：文本类型（TEXT），买家的文字评价
- **卖家评价**：文本类型（TEXT），卖家的文字评价
- **创建时间**：日期时间类型（DATETIME），交易创建的时间戳
- **更新时间**：日期时间类型（DATETIME），交易状态最后更新的时间戳
- **完成时间**：日期时间类型（DATETIME），可空，交易完成的时间戳，用于统计成交周期
- **同步版本号**：整数类型（INT），默认1

**业务规则：**
- **状态流转规则：** 待联系→已联系→约见中→已完成，只能正向流转，已完成或已取消的交易不能修改
- **评价机制：** 交易完成后双方可以互相评价，评分1-5分，评价提交后不可修改，评价影响用户的信用评分和评分
- **纠纷处理：** 交易过程中如有纠纷，可以发起举报，管理员介入处理，可以强制取消交易或退款

#### 8. 评论实体（Comment）

**实体描述：** 评论实体存储用户对商品的评论和问答，支持二级评论（回复）。评论可以是买家的购买反馈，也可以是潜在买家的咨询问题。支持点赞、举报、软删除等功能。

**主要属性：**
- **评论ID（主键）**：自增整数，唯一标识每条评论
- **商品ID（外键）**：整数类型，关联items表，表示评论所属的商品
- **用户ID（外键）**：整数类型，关联users表，表示评论者
- **父评论ID（外键）**：整数类型，可空，关联comments表自身，表示回复的目标评论，null表示顶级评论
- **评论内容**：文本类型（TEXT），评论的具体内容，最多500字
- **点赞数**：整数类型（INT），默认0，评论被点赞的次数
- **是否已删除**：布尔类型（BOOLEAN），默认false，软删除标记，删除后显示"该评论已被删除"
- **创建时间**：日期时间类型（DATETIME），评论发表的时间戳
- **更新时间**：日期时间类型（DATETIME），评论最后修改的时间戳
- **同步版本号**：整数类型（INT），默认1

- **软删除机制：** 评论删除后不物理删除，设置is_deleted=true，前端显示占位提示，保持评论楼层连续性

### 2.2.2 数据规范化分析

#### 第一范式（1NF）

**定义：** 表中的每个字段都是不可再分的原子值。

**本系统的实现：**

✅ **符合1NF的设计：**
- 所有表的字段都是原子值
- 用户信息（用户名、邮箱、手机）分开存储
- 时间字段独立（创建时间、更新时间）

⚠️ **使用JSON类型的字段：**
虽然JSON字段在物理上是复合类型，但在业务逻辑上作为整体使用，符合业务需求：
- `items.tags` - 商品标签数组，整体作为一个属性
- `system_configs.value` - 配置值，灵活存储不同类型配置
- `sync_logs.error_details` - 错误详情，便于记录复杂错误信息

**示例分析：**

❌ **不符合1NF（错误示例）：**
```sql
-- 联系方式字段包含多个值
CREATE TABLE users (
  contacts VARCHAR(500)  -- "手机:13800138000,邮箱:user@example.com"
);
```

✅ **符合1NF（正确设计）：**
```sql
CREATE TABLE users (
  phone VARCHAR(20),
  email VARCHAR(100)
);
```

#### 第二范式（2NF）

**定义：** 在1NF基础上，非主属性完全依赖于主键，不存在部分依赖。

**本系统的实现：**

✅ **消除部分依赖的设计：**

**示例1：商品图片表**
- 如果设计为 `(item_id, image_url)` 作为联合主键
- `sort_order` 和 `is_cover` 只依赖于完整的联合主键
- 采用单独的 `id` 作为主键，避免复杂依赖

**示例2：用户角色关联表**
```sql
-- 正确设计：使用独立主键
user_roles(
  id,           -- 独立主键
  user_id,      -- 完全依赖于id
  role_id,      -- 完全依赖于id
  created_at    -- 完全依赖于id
)

-- 而不是使用联合主键
-- PRIMARY KEY (user_id, role_id)
-- 这样created_at等字段完全依赖于整个主键
```

**不存在的部分依赖：**
- 所有表都使用单一主键（id），不使用复合主键
- 所有非主属性都完全依赖于主键

#### 第三范式（3NF）

**定义：** 在2NF基础上，消除传递依赖，非主属性不依赖于其他非主属性。

**本系统的实现：**

✅ **消除传递依赖的设计：**

**示例1：商品表优化**
```sql
-- 错误设计（存在传递依赖）：
items(
  id,
  seller_id,
  seller_name,      -- 依赖于seller_id
  seller_email,     -- 依赖于seller_id
  category_id,
  category_name,    -- 依赖于category_id
  ...
)

-- 正确设计（符合3NF）：
items(
  id,
  seller_id,        -- 通过外键关联users表
  category_id,      -- 通过外键关联categories表
  ...
)

users(id, username, email, ...)
categories(id, name, ...)
```

**示例2：交易表优化**
```sql
-- 正确设计
transactions(
  id,
  item_id,          -- 关联商品
  buyer_id,         -- 关联买家
  seller_id,        -- 关联卖家
  item_price,       -- 商品价格（冗余，但符合业务需求）
  final_amount,     -- 最终成交价
  ...
)

-- item_price 是冗余字段，但因为商品价格可能变化
-- 保存交易时的价格是业务需要，属于合理的反规范化
```

**合理的反规范化：**

为提升查询性能，某些字段进行了合理的反规范化：

1. **items表的统计字段**
   ```sql
   view_count,        -- 浏览量（避免COUNT查询）
   favorite_count,    -- 收藏量（避免JOIN统计）
   inquiry_count      -- 咨询量
   ```

2. **users表的统计字段**
   ```sql
   total_sales,       -- 总销售数
   total_purchases,   -- 总购买数
   seller_rating,     -- 卖家评分
   buyer_rating       -- 买家评分
   ```

3. **conversations表的冗余字段**
   ```sql
   last_message_content,  -- 最后消息内容（避免JOIN messages表）
   last_message_at,       -- 最后消息时间
   user1_unread_count,    -- 未读数量（避免COUNT查询）
   user2_unread_count
   ```

**反规范化说明：**
这些冗余字段通过触发器或应用层逻辑保持同步，在性能和规范性之间取得平衡。

#### BCNF（Boyce-Codd范式）

**定义：** 在3NF基础上，每个决定因素都是候选键。

**本系统的分析：**

✅ **符合BCNF的设计：**

本系统的所有表都符合BCNF，因为：
1. 所有表使用单一主键（id）
2. 所有函数依赖的决定因素都是主键
3. 不存在非平凡的函数依赖其决定因素不是候选键的情况

**唯一约束分析：**
```sql
-- users表
UNIQUE(username)     -- username → 所有其他属性
UNIQUE(email)        -- email → 所有其他属性
UNIQUE(student_id)   -- student_id → 所有其他属性

-- 这些都是候选键，符合BCNF
```

## 2.3 物理结构设计

### 2.3.1 存储引擎选择

#### MySQL/MariaDB存储引擎

**选用 InnoDB 引擎，理由如下：**

1. **事务支持（ACID）**
   - 完整的事务支持
   - 支持提交、回滚
   - 适合金融交易场景

2. **行级锁**
   - 并发性能好
   - 支持高并发写入
   - 减少锁竞争

3. **外键支持**
   - 虽然应用层维护外键
   - 但InnoDB提供了外键机制备用

4. **崩溃恢复**
   - 自动崩溃恢复
   - 数据安全性高

5. **缓存机制**
   - 缓冲池优化
   - 提高查询性能

**配置示例：**
```sql
CREATE TABLE items (
  ...
) ENGINE=InnoDB 
  DEFAULT CHARSET=utf8mb4 
  COLLATE=utf8mb4_unicode_ci
  ROW_FORMAT=DYNAMIC
  COMMENT='商品表';
```

#### PostgreSQL存储特性

PostgreSQL 不需要显式指定存储引擎，但具有以下优势：

1. **MVCC（多版本并发控制）**
   - 读写不阻塞
   - 高并发性能

2. **丰富的数据类型**
   - JSON/JSONB类型
   - 数组类型
   - 全文搜索类型

3. **强大的索引**
   - GIN索引（JSON）
   - GiST索引（全文搜索）
   - 部分索引

#### SQLite存储特性

1. **文件存储**
   - 单文件数据库
   - 便于备份和移动

2. **轻量级**
   - 适合开发和测试
   - 资源占用小

3. **嵌入式**
   - 无需服务器
   - 配置简单

#### conflict_records表（冲突记录表）⭐

**表用途：** 记录多数据库同步过程中发生的数据冲突。

**建表语句（MySQL）：**
```sql
CREATE TABLE conflict_records (
    id BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '冲突ID',
    table_name VARCHAR(100) NOT NULL COMMENT '表名',
    record_id VARCHAR(50) NOT NULL COMMENT '记录ID',

        DEFAULT 'pending' COMMENT '冲突状态',
    resolution ENUM('keep_source', 'keep_target', 'manual') COMMENT '解决方式',
    resolved_by BIGINT COMMENT '解决人ID',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP COMMENT '发现时间',
    resolved_at TIMESTAMP NULL COMMENT '解决时间',
    sync_version INT DEFAULT 0,
    
    INDEX idx_table (table_name),
    INDEX idx_status (status),
    INDEX idx_created (created_at),
    INDEX idx_source_target (source_db, target_db),
    INDEX idx_table_status (table_name, status),
```

**冲突类型说明：**

```sql
SELECT 
    table_name,
    COUNT(*) as total_syncs,
    SUM(CASE WHEN status = 'success' THEN 1 ELSE 0 END) as success_count,
    ROUND(SUM(CASE WHEN status = 'success' THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2) as success_rate,

FROM sync_logs
WHERE started_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
GROUP BY table_name;
```

### 2.5.2 数据库差异处理

不同数据库的SQL语法差异及处理：

**AUTO_INCREMENT差异：**
```sql
-- MySQL/MariaDB
id BIGINT PRIMARY KEY AUTO_INCREMENT

-- PostgreSQL
id BIGSERIAL PRIMARY KEY
-- 或
id BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY

-- SQLite
id INTEGER PRIMARY KEY AUTOINCREMENT
```

**JSON类型差异：**
```sql
-- MySQL
tags JSON

-- PostgreSQL
tags JSONB  -- 推荐使用JSONB，性能更好

-- SQLite
tags TEXT  -- 存储为文本
```

**ENUM类型差异：**
```sql
-- MySQL
status ENUM('pending', 'completed', 'cancelled')

-- PostgreSQL
-- 需要先创建类型
CREATE TYPE status_type AS ENUM('pending', 'completed', 'cancelled');
status status_type

-- SQLite (使用CHECK约束)
status TEXT CHECK(status IN ('pending', 'completed', 'cancelled'))
```

**时间戳差异：**
```sql
-- MySQL
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

-- PostgreSQL
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
-- 需要触发器实现ON UPDATE

-- SQLite
created_at DATETIME DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
-- 需要触发器实现ON UPDATE
```
