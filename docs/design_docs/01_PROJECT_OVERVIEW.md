# 凤凰汽配管理系统 - 项目概述文档

## 1. 引言

### 1.1 编写目的
本项目的核心目标是为“凤凰汽配”提供一套高效、稳定、易用的数字化管理平台。随着汽车后市场的快速发展，传统的汽配管理模式已无法满足日益增长的业务需求。本系统旨在通过现代化的信息技术，实现零件库存、交易订单、客户关系以及系统监控的全面自动化管理。

本文档作为项目设计的起始章节，详细描述了系统的背景、目标、业务范围以及相关术语，为后续的详细设计、开发和测试提供统一的指导方针。

### 1.2 项目背景
在当前的汽配行业中，企业面临着零件种类繁多（SKU量大）、库存周转率要求高、交易环节复杂等挑战。原有的系统（如 Campus Swap 改造前版本）主要针对校园二手交易，无法处理汽配行业特有的复杂逻辑，如零件兼容性、大批量采购、多级分类等。

“凤凰汽配管理系统”是在原有架构基础上，经过深度重构和业务重塑而成的专业化管理平台。它不仅继承了原系统的分布式架构优势，更针对汽配业务进行了全方位的定制化开发。

## 2. 项目目标

### 2.1 业务目标
1. **库存精准化**：实现零件库存的实时监控，支持多仓库、多库位管理，确保库存准确率达到 99.9% 以上。
2. **交易高效化**：简化采购与销售流程，支持快速下单、自动审核及订单追踪，缩短交易周期。
3. **决策数据化**：通过仪表盘实时展示成交额、咨询量、库存预警等关键指标，为管理层提供决策支持。
4. **服务专业化**：集成 AI 助手，提供零件识别、兼容性查询及智能客服功能，提升客户满意度。

### 2.2 技术目标
1. **高可用性**：系统需支持 7x24 小时不间断运行，核心业务可用性不低于 99.95%。
2. **高性能**：支持万级 SKU 的快速检索，API 平均响应时间控制在 200ms 以内。
3. **可扩展性**：采用微服务化设计思想，支持根据业务增长动态扩展计算资源。
4. **安全性**：建立完善的 RBAC（基于角色的访问控制）体系，确保敏感数据（如成本价、客户信息）的绝对安全。

## 3. 业务范围

### 3.1 核心功能模块
- **零件管理**：包括零件录入、分类管理、图片上传、兼容车型维护。
- **库存中心**：入库管理、出库管理、库存盘点、低库存预警。
- **交易系统**：采购车功能、订单生成、支付状态跟踪、退换货处理。
- **用户与权限**：管理员、仓库员、销售员、普通客户的多角色管理。
- **智能监控**：系统性能监控、操作审计日志、AI 业务分析。

### 3.2 非业务功能
- **系统配置**：全局参数设置、数据备份策略。
- **日志管理**：系统运行日志、异常堆栈追踪。

## 5. 约束与限制

### 5.1 开发约束
- 后端必须使用 Python FastAPI 框架。
- 前端必须使用 Vue 3 + TypeScript + Naive UI。
- 数据库统一使用 MySQL，移除所有多库同步逻辑。

### 5.2 运行约束
- 系统需部署在 Docker 容器化环境中。
- 客户端浏览器建议使用 Chrome 90+ 或 Edge 90+。

## 8. 风险管理与应对 (Risk Management)

### 8.1 技术风险
- **风险描述**：AI 识别模型在复杂背景下识别率低。
- **应对措施**：增加数据增强处理，引入多模型融合技术，提供人工纠错机制。

### 8.2 进度风险
- **风险描述**：第三方支付/物流接口联调耗时超预期。
- **应对措施**：提前申请沙箱环境，编写 Mock 接口进行并行开发。

### 8.3 数据风险
- **风险描述**：旧系统数据格式混乱，迁移困难。
- **应对措施**：成立专门的数据清洗小组，制定严格的校验规则。

## 9. 质量保证体系 (Quality Assurance)
1. **代码评审 (Code Review)**：所有代码必须经过至少一名资深开发人员评审。
2. **持续集成 (CI)**：每次提交自动触发单元测试和静态代码检查。
3. **灰度发布**：新功能先在小范围用户中试用，确认稳定后再全量推送。
4. **用户反馈循环**：建立快速响应机制，收集用户意见并定期迭代。

### 1.7 名词解释 (Glossary)

为了确保项目相关方对专业术语有统一理解，特制定本术语表：

| 术语 | 全称/定义 | 说明 |
| :--- | :--- | :--- |
| **OE 号** | Original Equipment Number | 汽车主机厂对零件的原始编号，是汽配识别的唯一标准。 |
| **SKU** | Stock Keeping Unit | 库存进出计量的单位，在本项目中指代具体的零件规格。 |
| **RBAC** | Role-Based Access Control | 基于角色的访问控制，系统权限管理的核心机制。 |
| **JWT** | JSON Web Token | 用于前后端身份验证的安全令牌。 |
| **ORM** | Object-Relational Mapping | 对象关系映射，用于将 Python 类映射到数据库表。 |
| **SPU** | Standard Product Unit | 标准产品单位，一组具有相同属性的零件集合。 |
| **安全水位** | Safety Stock Level | 触发库存预警的最低库存数量。 |

### 1.8 质量保证计划 (QA Plan)

为确保系统达到企业级应用标准，制定以下质量保证措施：

#### 1.8.1 代码质量控制
-   **静态分析**：集成 `ruff` 和 `mypy`，在 CI 阶段强制执行代码风格和类型检查。
-   **代码评审**：所有合并到 `main` 分支的代码必须经过至少一名高级开发人员的 Review。

#### 1.8.2 测试覆盖率要求
-   **核心业务逻辑**：Service 层单元测试覆盖率必须达到 90% 以上。
-   **API 接口**：所有公开接口必须编写集成测试用例。

#### 1.8.3 性能指标 (KPI)
-   **响应时间**：95% 的非报表类 API 请求响应时间应小于 200ms。
-   **并发能力**：单机支持至少 100 个并发连接而不出现超时。
-   **可用性**：系统年度可用率目标为 99.9%。

#### 1.8.4 文档规范
-   所有 API 必须有完整的 Swagger/OpenAPI 文档。
-   数据库变更必须附带 Alembic 迁移脚本及说明。
-   关键算法（如库存周转率）必须有详细的技术设计文档。
